# Support Brain for SaaS — Interaction Principles

## 1. Dominant interaction posture: Coordinate and Command
The core interaction feeling is not:
- approve an AI suggestion,
- triage isolated issues one by one,
- investigate one object and stop.

It is:
**the support lead standing above the support system and issuing coordinated moves across queues, teams, knowledge objects, and channels.**

The user should feel:
- I am not just reading alerts,
- I am not just reviewing evidence,
- I am changing how the support system will operate next.

## 2. The five interaction levels

### Level 1: Notice movement
The system first shows where change is happening.

### Level 2: Interpret relevance
The system helps the user judge why that movement matters, who it affects, and whether it deserves intervention.

### Level 3: Choose intervention
The user decides:
- who should own it,
- what should move first,
- what publication should be constrained,
- which route should escalate.

### Level 4: Issue command
The user performs a coordination action.

### Level 5: Confirm propagation
The system must reflect:
- which objects changed,
- which teams are affected,
- which surfaces are already in sync,
- what remains unresolved.

## 3. Top-level interaction principles

### Principle A: System before object
The default entry should show system movement before object inventory.

### Principle B: Coordination before editing
If the real job is to change priority or routing, the product should not force the user into editing depth first.

### Principle C: Every action needs scope
Every command should answer:
- what objects it affects,
- which audiences it affects,
- which downstream surfaces it affects,
- whose order of work it changes.

### Principle D: Allow drill-down without losing command posture
Users can go deep into evidence, but the product must not let them forget they are still commanding a wider system.

### Principle E: Supporting surfaces inherit the rhythm of the main system
Copilot, frontline, and external answer surfaces should not define the rhythm of the control tower.

## 4. Action hierarchy
### Layer 1: Judgment actions
- set priority,
- confirm blast radius,
- identify ownership.

### Layer 2: Coordination actions
- route,
- assign,
- escalate,
- reorder attention.

### Layer 3: Governance actions
- start review,
- adjust audience variants,
- change publish visibility,
- demand stronger evidence.

### Layer 4: Verification actions
- inspect propagation,
- inspect rewrite reduction,
- inspect drift convergence.

## 5. What a command should not feel like
A command should not feel like:
- clicking a button while the system disappears into automation,
- approving one AI suggestion and ending there,
- losing context after a page jump.

A command should feel like:
- an explicit system move,
- a clear scope of effect,
- traceable responsibility and consequence,
- something that can later be verified.

## 6. Drill-down boundaries
Drill-down matters, but it is secondary.
It exists to explain:
- why an issue is worth moving,
- why an audience is affected,
- why an object became a risk center.

It must not rewrite the narrative into:
“this is mainly a content editing product.”

## 7. Conflict and unresolved state
The value of this system comes partly from exposing what is not closed.
The product should let users clearly perceive:
- a command has not fully propagated,
- an object conflicts with another rule,
- a source is still unreliable,
- a queue still lacks ownership.

Do not hide conflict in the name of smoothness.

## 8. Supporting-surface interaction role
### Copilot surface
Its main interaction meaning is feedback:
- which governed knowledge is truly adopted,
- which knowledge is still corrected by humans,
- which suggestions should rise back into the control tower.

### External answer surface
Its role is propagation outcome, not the primary theater of interaction.

## 9. Feedback rules
Good feedback is not just “success.”
It should tell the user:
- what changed,
- who is affected first,
- what is already in sync,
- what still needs a follow-up move.

## 10. Dangerous experience drifts
If the interaction starts making the user feel:
- “I mainly approve AI,”
- “I mainly browse evidence,”
- “I mainly edit an article,”
- “I mainly process tickets,”
then the design is drifting.

The intended feeling is:
- “I am reordering the support system,”
- “I am deciding what the organization handles first,”
- “I am bringing downstream answer behavior back into alignment.”

## 11. Interaction validation questions
Every key action should answer:
- Is this an observation action, coordination action, or governance action?
- Does the user know the scope?
- Does the user know where the action goes next and who it affects?
- Does the system show propagation results rather than only completion?
