# Support Brain for SaaS — 前端行为 Story

## 1. 写作约束
这份文档只描述两件事：
- 用户行为
- 系统预期行为

它**不描述**：
- 组件实现
- 前端技术栈
- API 设计
- 视觉像素稿

## 2. 前端总姿态
用户进入系统时，不应该像进入“工作台”。

他们进入的是：
**一个可以看到系统变化、调整优先级、发出协调动作的支持指挥层。**

因此所有页面族都要遵守一个顺序：
1. 先让用户看见哪里在动
2. 再让用户判断哪里该动
3. 最后让用户下达动作，并看到动作传播

### 语言行为（中文优先）
- 默认中文体验；提供中 / 英切换，英文是次选但仍是完整体验。
- 界面外壳（分区标题、命令名展示、状态、提示、空/错/重试态）随语言切换。
- 知识内容（对象标题、why-now、headline）由后端提供并保持英文，前端不翻译内容本身。

## 3. 页面族 1：Command Center

### 用户行为
- 进入系统后先扫描全局变化
- 比较不同队列、主题、audience、channel 的压力变化
- 识别今天最需要干预的事项
- 判断哪些问题是局部的，哪些问题正在扩散

### 系统预期行为
- 自动把最值得领导干预的变化排到前面
- 让“变化”和“影响范围”比静态对象更先被看见
- 让用户一眼知道哪些问题关联 release、incident、policy 或 publish
- 让用户能直接进入下一层协调，而不必先浏览无关对象

## 4. 页面族 2：Queue / Topic Coordination

### 用户行为
- 选择某个正在失控或升温的队列/主题
- 判断它影响的是谁、为什么现在重要、应该由谁处理
- 在多个队列之间比较优先级
- 为不同队列下达不同的后续动作

### 系统预期行为
- 展示该队列/主题与知识对象、audience、source、feedback 的关联
- 把“需要哪个团队介入”变成显式信息
- 允许用户从队列层直接路由、升级、转入 review 或 publish
- 在做出动作前显示其下游影响范围

## 5. 页面族 3：Knowledge Review Queue

### 用户行为
- 查看哪些知识建议、修订、紧急变更需要审阅
- 判断哪些草稿该优先处理
- 决定是通过、驳回、补证据，还是转交他人

### 系统预期行为
- 不是简单列草稿，而是突出“为什么它现在重要”
- 显示该草稿关联的风险、受影响 audience、下游 surface 和证据强度
- 让用户能够批量地协调审阅顺序，而不是逐条被动处理
- 保留“需要更多证据”的中间态，不逼迫假确定性

## 6. 页面族 4：Knowledge Object Workspace

### 用户行为
- 进入某个 Answer Card / Troubleshooting Flow / Policy Rule / Known Issue Page
- 理解它当前状态、版本、证据来源与 audience 适用范围
- 判断这个对象是应该修改、分化 audience、还是暂时降级外部可见性

### 系统预期行为
- 先呈现对象的 operational meaning，而不是先呈现全文编辑器
- 让用户快速看到它现在影响了哪些 surface、哪些 audience、哪些队列
- 让版本变化、例外条件、历史 superseded 关系容易理解
- 在对象层就能发起协调动作，而不是被迫跳回首页

## 7. 页面族 5：Audience / Publish Rules

### 用户行为
- 查看某个对象当前被哪些 audience 与 channel 消费
- 判断是否需要限制、放开、分化或延迟发布
- 在变更前确认 blast radius

### 系统预期行为
- 让 audience 差异和 channel 差异成为显式操作对象
- 在用户下达 publish / unpublish / restrict 动作前，先呈现谁会受影响
- 呈现 internal 与 external surface 的差异后果
- 在动作后回显传播状态，而不只是回显“已成功”

## 8. 页面族 6：Sources / Evidence Health

### 用户行为
- 查看哪些 source 正常、哪些 source 过期、哪些 source 在失败
- 判断某个知识问题到底是内容错、来源错，还是同步错
- 决定是否先修 source，再修 object

### 系统预期行为
- 把 source 健康度与知识风险连起来，而不是单独做一个后台页
- 让来源异常能被追溯到具体对象和具体 downstream 影响
- 让“source 问题导致的知识问题”比技术日志更容易被产品用户理解

## 9. 页面族 7：Copilot / Downstream Surface Feedback

### 用户行为
- 查看 control tower 的命令是否改变了 frontline 实际使用情况
- 观察哪些建议仍被改写、拒绝或升级
- 判断系统是否真的恢复同步

### 系统预期行为
- 把 rewrite、reject、escalate 当作 control feedback，而不是孤立事件
- 让用户看到哪些表面仍在偏离已发布知识
- 让 downstream 行为变化可以反推上游治理优先级

## 10. 页面族之间的行为链

### 行为链 A：从全局风险到协调动作
用户先在 Command Center 看见异常，再进入 Queue / Topic Coordination，下达路由、review 或 publish 命令。

### 行为链 B：从对象问题到系统影响
用户先从某个对象进入 Workspace，再看 audience 与 publish 影响，最后调整下游传播。

### 行为链 C：从反馈异常到治理回路
用户先在 Copilot / feedback 面看到大量重写，再回到对象、队列或来源层做干预。

## 11. 前端行为的禁忌
前端 story 不应该让用户感觉自己在：
- 一条条处理 ticket
- 一条条审批 AI 建议
- 一层层浏览知识库目录
- 被动地看 dashboard 然后什么也改不了

它应该让用户感觉自己在：
- 发现变化
- 设定优先级
- 分配干预动作
- 观察整个支持系统是否重新同步

## 12. 行为 Story 的检验标准
如果某个页面无法回答下面至少一个问题，这个页面就偏离了完整 story：
- 它帮助用户看见了什么系统级变化？
- 它帮助用户决定了什么优先级？
- 它让用户发出了什么协调动作？
- 它让用户看到了什么下游传播结果？
