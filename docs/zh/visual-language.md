# Support Brain for SaaS — 视觉语言方案

## 1. 目标
这套视觉语言不是为了“看起来很 AI”。

它的目标是让用户一进入系统，就感到：
- 这里是高信号环境
- 这里的层级服务于判断
- 这里的状态服务于指挥
- 这里不是聊天，不是 CMS，不是 BI 皮肤

## 2. 主气质：Mission Control
Mission control 在这里不是科幻风格词，而是一组感知要求：
- **全局感**：用户总能感知自己在看整个支持系统，而不是单页局部
- **优先级感**：重要的事会往前浮，不重要的事会退后
- **风险感**：异常、漂移、冲突、阻塞要比正常状态更容易被感知
- **协调感**：页面不只是“展示对象”，而是在展示对象之间如何联动

## 3. 不是哪几种视觉
它不应像：
- 柔和温暖的客服工作台
- 彩色 BI dashboard
- 带很多 AI glow 的 agent studio
- 纯文档系统或知识库后台

## 4. 视觉层级顺序
这套产品的视觉层级应该优先强化以下顺序：
1. **系统级变化**
2. **优先级与风险**
3. **队列 / topic / audience 的受影响范围**
4. **知识对象状态**
5. **证据与细节**

如果证据块、表单块、对象正文总是比风险和优先级更抢眼，视觉就偏了。

## 5. 色彩语义

### 基础色
- 应以中性、克制、技术感底色为主
- 支持高密度信息，不制造噪音
- 允许暗色倾向，但不强制科幻黑

### 语义色
- **蓝色**：可执行、可信赖、已纳入控制层的动作与状态
- **黄色/琥珀色**：需要协调、等待判断、传播风险未闭合
- **红色**：高风险漂移、错误外露、已知问题爆发、发布阻塞
- **绿色**：确认恢复一致、确认已传播、确认风险收敛

### 原则
- 不允许“只是为了丰富界面”而增加语义色
- 颜色必须帮助判断，不是帮助装饰
- 状态不能只靠颜色表达

## 6. 字体与数字
- 字体应传达稳健、准确、专业，而不是科技噱头
- 指标、数量、时间、版本号应优先支持表格式阅读
- 数字应是“可判断的运营信号”，不是点缀
- 标题层级应更像操作层级，而不是营销排版层级

## 7. 布局节奏
- 布局要体现“从全局到局部”的层层下潜
- 不应该让用户一进来就陷入卡片海洋
- 面板应形成控制台节奏，而不是内容 feed 节奏
- 留白要服务于分组和层级，而不是营造空旷感

## 8. 面板与容器
- 容器应有明确层级感，但不应过度拟物
- 分隔优先依靠结构、边界、对齐和密度差，而不是花哨阴影
- 面板应支持“并列比较”和“快速切换上下文”
- 同一屏里，至少要能容纳“系统信号 + 协调对象 + 后果预览”三种信息层

## 9. 图标与图形
- 图标优先使用方向性、状态性、关系性语义
- 应偏向 route、link、propagate、scope、queue、publish 这类支持操作语义
- 避免把 chat bubble 作为整个系统的默认隐喻
- 小型图形更适合作为系统 movement 的辅助，而不是视觉主角

## 10. 动效
- 动效只服务三件事：
  1. 状态变化
  2. 指挥动作已传播
  3. 上下文切换
- 动效应短、准、低戏剧性
- 不应通过动画制造“AI 在思考”的幻觉
- 减少运动模式下仍要保留因果清晰度

## 11. 视觉上的细节边界
这套视觉方案值得刻意强调的细节包括：
- 优先级越高，视觉位置和状态语义越前置，而不是单纯越红
- 正常状态要学会后退，避免界面被“成功状态”刷满
- 需要协调的状态，比“已经完成”的状态更应获得注意力
- 传播后果要有独立视觉存在，不应只藏在二级详情里

## 12. 应避免的误导
如果出现以下感觉，就说明视觉偏离了：
- “这是 AI 产品，所以要多一点发光和渐变”
- “这是 dashboard，所以到处都应该有图表”
- “这是知识产品，所以正文必须最大”
- “这是支持工具，所以聊天感要最强”

## 13. 落地时的视觉检验问题
任何页面都应该回答：
- 用户是否能立刻分辨哪里是系统级变化，哪里只是对象详情？
- 协调动作是否比装饰元素更显眼？
- 风险、阻塞、未闭合状态是否真的会被先看到？
- 用户是否会感觉自己在看一个被治理的系统，而不是一个内容仓库？
