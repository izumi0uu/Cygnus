# Support Brain for SaaS — Visual Language

## 1. Goal
This visual system is not trying to “look AI.”

Its goal is to make the user feel immediately that:
- this is a high-signal environment,
- hierarchy exists to support judgment,
- state exists to support command,
- this is not chat, not a CMS, and not a BI skin.

## 2. Dominant mood: Mission Control
“Mission control” here is not a sci-fi theme word. It is a set of perception requirements:
- **Global awareness**: the user should feel they are seeing the support system, not a local page fragment.
- **Priority awareness**: what matters rises forward, what does not recedes.
- **Risk awareness**: drift, conflict, spread, and blockage should surface before healthy routine state.
- **Coordination awareness**: the product should reveal how objects and surfaces relate, not just present isolated objects.

## 3. What it should not look like
It should not resemble:
- a warm frontline support workspace,
- a colorful BI dashboard,
- an agent studio with glowing AI theatrics,
- a document backend or knowledge CMS.

## 4. Visual hierarchy order
The system should visually prioritize this sequence:
1. **system-level movement**
2. **priority and risk**
3. **affected queue/topic/audience scope**
4. **knowledge object state**
5. **evidence and detail**

If evidence blocks, forms, or object bodies constantly outshine risk and priority, the visual hierarchy is wrong.

## 5. Color semantics
### Base color
- Neutral, restrained, technical foundation
- Able to support dense information without noise
- Dark-leaning is allowed, but sci-fi black is not required

### Semantic color
- **Blue**: trusted action, governed control, routable command
- **Amber**: coordination needed, judgment pending, propagation not yet closed
- **Red**: high-risk drift, externally exposed wrongness, incident-linked instability, publish blockage
- **Green**: confirmed re-alignment, confirmed propagation, converged risk

### Rules
- Do not add semantic colors for decoration.
- Color must help judgment, not ornament.
- Status cannot depend on color alone.

## 6. Typography and numbers
- Typography should signal steadiness, precision, and operational seriousness.
- Metrics, counts, timestamps, and versions should support tabular reading.
- Numbers should act as decision signals, not ornaments.
- Title hierarchy should feel operational, not promotional.

## 7. Layout rhythm
- Layout should support a macro-to-micro descent.
- Users should not land in a sea of visually equivalent cards.
- Panels should feel like console surfaces, not content feeds.
- Whitespace should serve grouping and hierarchy, not emptiness for its own sake.

## 8. Panels and containers
- Containers should have clear hierarchy without heavy skeuomorphism.
- Separation should rely on structure, edges, alignment, and density more than theatrical shadows.
- Panels should support side-by-side comparison and fast context switching.
- A single screen should be able to hold at least: system signal + coordination object + downstream consequence.

## 9. Iconography and small graphics
- Icons should prioritize direction, state, and relationship semantics.
- Prefer route, link, propagate, scope, queue, and publish metaphors.
- Do not let the chat bubble become the default product metaphor.
- Small graphics should assist system movement, not become the visual protagonist.

## 10. Motion
- Motion should serve only three things:
  1. state change,
  2. propagation of a command,
  3. context switching.
- Motion should be short, precise, and low-drama.
- It should not simulate “AI thinking.”
- Reduced-motion mode should preserve causal clarity.

## 11. Detail boundaries worth protecting
- Higher priority should move forward through position and state, not just redness.
- Healthy default state should learn to recede.
- Coordination-needed state should often be louder than already-completed state.
- Downstream consequence should have independent visual presence.

## 12. Misleading visual instincts to avoid
If the design starts to imply any of these, it is drifting:
- “This is an AI product, so it needs glow and gradients.”
- “This is a dashboard, so everything needs charts.”
- “This is a knowledge product, so object body text must dominate.”
- “This is a support tool, so chat should define the whole feel.”

## 13. Visual validation questions
Every screen should be able to answer:
- Can the user instantly tell system movement from object detail?
- Are coordination moves more salient than decoration?
- Do risk, blockage, and unresolved states truly surface first?
- Does the product feel like a governed system rather than a content repository?
